If you leave a iron hammer in a dry shed for thirty years, you can pick it up today and drive a nail. The handle might look a little weathered, but the fundamental mechanics remain untouched.

Software doesn't work like that, which is strange when you think about it. Digital bits don’t oxidize. A compiled binary sitting on a hard drive in 1998 has the exact same arrangement of ones and zeroes today. It hasn't decayed by a single atom.

And yet, if you try to run that binary today, it almost certainly won't work.

We often call this "bit rot," but the name is a misnomer. The bits aren't rotting; everything *around* them moved. The operating system updated its graphics pipeline. The processor architecture shifted. Security standards evolved to treat old unencrypted network calls like biohazards.

Physical tools break because the world wears them down. Software breaks because the world leaves it behind.

There’s a subtle lesson here about maintenance. In the physical world, conservation is about protecting an object from change. In software, conservation is about changing the object fast enough to keep up with the floor sliding beneath it. To keep a piece of software alive, you don't lock it in a vault—you constantly edit it, recompile it, and rewire its connections to the modern web.

Static perfection in code is an illusion. The digital artifacts that survive fifty years won't be the most beautifully engineered ones sitting silently in cold storage; they'll be the messy ones attached to a community willing to keep editing them forever.
